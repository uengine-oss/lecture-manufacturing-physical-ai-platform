## 이번 회차에서 할 일

4회에 만든 관제 화면(B9)은 로컬 관제 API 한 곳만 읽었다. 이번 회차의 제조 운영 앱은 세 곳을 함께 읽는다. 설비·사건 목록은 7회에 발행한 Ontology Studio 객체에서, 사건 상세와 온도 추이는 관제 API 에서, 업무 진행은 8회에 연결한 프로세스에서 가져온다. 화면 코드(Vue)는 제공본을 그대로 쓰고, 우리는 **어디서 읽을지 정하는 설정과 주소의 빈칸**만 채운 뒤 교육용 플랫폼(Lab Platform)의 Apps 기능으로 게시한다. 끝나면 앱 URL 하나로 같은 사건의 데이터·업무 진행·조치 기록을 확인할 수 있다.

### 학습 목표
- 앱 설정 `window.APP_CONFIG` 의 네 값이 각각 어느 서버·스키마·프로세스를 가리키는지 설명할 수 있다.
- 화면의 설비 목록·사건 목록·사건 상세·업무 인스턴스 조회 주소를 채우고 실제 GET 결과로 확인할 수 있다.
- 앱을 게시하고 게시 로그의 네 단계(검증·번들·상태 확인·게시 완료)를 읽을 수 있다.
- 시뮬레이터 조치 후 앱에서 다시 조회해 화면·프로세스·조치 기록이 같은 event_id 를 가리키는지 확인할 수 있다.

## 2. 핵심 개념

![하나의 사건이 통과하는 경로](../../materials/diagrams/D02_event_path.png)

제조 운영 앱은 `system/labplatform/app_templates/ops-console/` 의 정적 파일 세 개(`index.html`, `vue.global.prod.js`, 게시 때 생기는 `config.js`)로 되어 있다. 화면이 읽는 곳을 표로 정리하면 다음과 같다.

| 화면 칸 | 읽는 곳 | 계층 |
|---|---|---|
| 설비 (Ontology: Asset) | `POST {platform_api}/studio/schemas/{schema_name}/objects/Asset/fetch` (읽기 전용 조회) | Ontology |
| 사건 (Asset —HAS_EVENT→ Event) | `GET {platform_api}/studio/schemas/{schema_name}/objects/Asset/{asset_id}/related/HAS_EVENT` | Ontology |
| 온도 추이 | `GET {hydops_api}/api/series?asset_id=…&seconds=180` | Data Sources (관제 API) |
| 사건 기록 | `GET {hydops_api}/api/events/{event_id}` | 관제 API |
| 업무 진행 | `GET {platform_api}/process/instances/{instance_id}`, `GET {platform_api}/process/worklist` | Orchestration |
| 업무 열기 버튼 | `POST {platform_api}/process/definitions/{process_def_id}/start` | Orchestration |

화면은 2초마다(`setInterval(this.tick, 2000)`) 온도 추이·사건 목록·선택 사건을 다시 읽는다.

> **주의 — 앱 게시는 화면만 올리는 일이다.** 분석·시뮬레이터 서버(:8800)와 교육용 플랫폼(:8910)은 강사가 미리 운영한다. 게시가 성공해도 바인딩한 서버가 멈춰 있으면 화면은 비어 보인다. 게시 로그의 "상태 확인" 단계가 그 차이를 알려 준다.

> **주의 — "같은 사건 확인" 세 개의 ✔ 는 설비 회복을 뜻하지 않는다.** 화면 event_id·프로세스 입력 event_id·조치 기록 event_id 가 같다는 연결 검사일 뿐이다. 회복 여부는 사건 기록의 "재측정" 줄로 읽는다.

## 4. 활동 2 — 선택 사건의 업무 시작·상태 조회 버튼 연결 · 50분

### 목표
사건을 고르면 사건 상세 → 대응된 업무 인스턴스 → 워크리스트 순서로 읽고, "업무 열기" 버튼이 같은 사건 값으로 업무를 시작하도록 주소를 채운다.

### 따라 하기
1. 제공 화면의 두 메서드를 읽는다.

```javascript
async refreshEvent() {
  if (!this.eventId) return;
  this.detail = await get(`${cfg.hydops_api}/api/events/${this.eventId}`);
  const ref = this.detail.event.process_ref;
  if (ref) this.instance = await get(`${cfg.platform_api}/process/instances/${ref.instance_id}`);
  ...
},
async openWork() {
  const e = this.detail.event;
  const r = await post(`${cfg.platform_api}/process/definitions/${cfg.process_def_id}/start`, { values: { event_id: e.event_id, asset_id: e.asset_id, run_id: e.run_id, event_type: e.event_type } });
  this.startMsg = r.duplicate ? `이미 시작된 업무 ${r.instance_id} 를 엽니다 (중복 시작 없음)` : `업무 ${r.instance_id} 시작`;
  ...
},
```

2. `app_bindings.js` 의 `eventDetail`·`processInstance`·`openWork` 빈칸을 채운다.
3. 에이전트·조치 담당은 `same_event.py` 의 빈칸을 채운다. 화면의 computed `sameUi`·`sameProcess`·`sameAction` 과 같은 판정이다.
4. 사건 상세와 인스턴스를 GET 으로 읽는다.

```bash
curl -s http://localhost:8800/api/events/EVT-20260914-131041-HYD-01-f81e | python3 -c "import sys,json;d=json.load(sys.stdin);print(d['event']['process_ref']);print([a['event_id'] for a in d['actions']])"
curl -s http://localhost:8910/process/instances/PI-75788b6a | python3 -c "import sys,json;i=json.load(sys.stdin);print(i['status'],i['business_result'],i['equipment_outcome'],i['vars']['event_id'])"
```

5. 테스트를 모두 돌린다: `PYTHONPATH=. .venv/bin/python -m pytest ../labs/integrated/S09 -q`

반대로 로컬 모드에서 처리된 사건(예: …-07b0)은 `process_ref` 가 `null` 이다. 이때 화면은 인스턴스를 읽지 않고 "업무 열기" 버튼을 보여 준다.

### 흔한 실수
- "업무 열기"를 여러 번 누르면 인스턴스가 여러 개 생긴다고 생각하는 것. 인스턴스 키 `cooling_response:event_id:1` 이 이미 있으면 새로 만들지 않고 기존 인스턴스를 연다(화면 문구 "중복 시작 없음").
- 이미 끝난 로컬 사건(`process_ref` 가 `null` 인 CLOSED·ESCALATED 사건)에서 "업무 열기"를 누르는 것. 버튼은 보이지만 새 업무는 **열린 사건**에만 시작한다. 수업에서는 새로 감지된 사건에서만 누른다.
- 조치 기록이 없는 사건(거부·센서 오류)에서 세 번째 확인이 ✘ 라고 적는 것. 화면은 "— 조치 기록 없음 (실행 전 종료)"로 표시하고, `same_event.py` 는 `None`(해당 없음)을 돌려준다.

## 6. 활동 4 — 시뮬레이터 조치·재조회와 재시작 연습 · 50분

### 목표
새 사건이 생기고 조치·재측정이 끝날 때까지 앱에서 다시 조회해 기록이 채워지는 순서를 보고, 서버 재시작 뒤에도 같은 사건을 같은 앱 URL 에서 다시 찾는다.

### 따라 하기
1. 강사가 관제 화면(:8800)에서 HYD-01 에 **냉각 성능 저하** 를 주입한다. 앱의 온도 추이가 60°C 점선 위로 올라가는지 본다.
2. 새 사건이 사건 목록에 나타나면 누르고, **업무 열기** 를 누른다(강사가 Watch 를 이미 돌렸다면 "이미 시작된 업무 … 를 엽니다" 문구가 뜬다).
3. 업무 진행 칸에 "조치 승인" 카드가 뜨면 결정·승인값·승인자를 넣고 **제출** 한다.
4. 사건 기록 칸이 명령 → 재측정 순으로 채워지는 동안 기록 표에 시각을 적는다.

| 시각 | 사건 status | 업무 현재 단계 | 명령 결과 | 재측정 |
|---|---|---|---|---|
| (기록) | PENDING_APPROVAL | 조치 승인 | — | — |
| (기록) | VERIFYING | 조치 후 재점검 | SUCCEEDED | — |
| (기록) | CLOSED 또는 ESCALATED | 종결 또는 담당자 이관 | SUCCEEDED | RECOVERED 또는 NOT_IMPROVED |

5. **재시작 연습(강사 시연).** 강사가 `scripts/servers.sh platform 4` 로 두 서버를 다시 띄운다. 학생은 같은 앱 URL 을 새로고침하고, 방금 사건을 다시 눌러 기록을 대조한다.

### 확인 포인트
- 조치 후 재측정 기준은 교육용 가정값이다: 조치 30초 뒤부터 60초 창에서 55°C 이하가 10초 연속이면 RECOVERED(`hydops/config.py`). 8회 기록의 …-f81e 는 `longest_below_s 56`, `valid_ratio 1.0` 으로 RECOVERED 였다.
- 명령 결과 줄(SUCCEEDED)이 먼저 생기고, 재측정 줄은 창이 끝난 뒤에 생긴다. 두 줄이 동시에 채워지지 않는다는 점을 표의 시각으로 확인한다.
- 재시작 뒤 코드상 달라지는 것과 남는 것은 다음과 같다. 수업에서는 실제로 본 결과를 표에 적는다.

| 항목 | 재시작 뒤 | 근거 코드 |
|---|---|---|
| `run_id` | 새 값 | `Plant.reset` → 새 `PlantRuntime` |
| 이전 실행의 열린 사건 | `RUN_ENDED` 로 닫힘 (회복으로 기록하지 않음) | `store.end_open_events_of_other_runs` |
| 온도 추이 그래프 | 새 실행 관측만 표시 | `/api/series` 가 현재 `run_id` 로 조회 |
| 사건 목록·사건 기록 | 이전 사건도 그대로 조회 | HAS_EVENT 는 `run_id` 조건 없이 조인 |
| 게시 앱·프로세스 인스턴스·인스턴스 키 | 그대로 | 교육용 플랫폼 메타데이터가 PostgreSQL `labplatform.doc` 에 저장 |

### 흔한 실수
- 명령이 SUCCEEDED 로 바뀌자마자 "회복"이라고 발표하는 것. 심각한 저하(냉각 0.25)에서는 명령이 성공해도 재측정이 NOT_IMPROVED 로 끝나 이관된다(`out/e2e_platform_report.json` "조치 후 미개선").
- 재시작 뒤 온도 그래프가 비었다고 데이터가 지워졌다고 생각하는 것. 그래프는 현재 실행만 그린다. 이전 사건 기록은 사건 목록에서 그대로 열린다.
- 실패한 인스턴스가 남긴 열린 사건 때문에 새 사건이 안 생기는 경우를 서버 고장으로 보는 것. 설비·유형당 열린 사건은 하나라서 새 감지가 막힌다. 시뮬레이터 초기화가 이전 실행의 열린 사건을 `RUN_ENDED` 로 닫는 이유다.

- `scripts/servers.sh platform 4` 후 `scripts/bootstrap_platform.py --upto watch` (앱 게시는 학생이 한다). 리허설로 이미 게시했다면 같은 이름으로 다시 게시하면 폴더를 지우고 새로 만든다.
