## 이번 회차에서 할 일

1~5회차는 모든 블록을 로컬 코드로 연결했다. 오늘부터 후반부 플랫폼 연결을 시작한다. 수업에서는 실제 uEngine 플랫폼의 개념과 API 모양을 재현한 **교육용 플랫폼(Lab Platform, `http://localhost:8910`)** 을 쓴다. 오늘 다루는 것은 Data Sources 계층의 Data Fabric 과 Ontology 계층의 Ontology Studio 다. 강사가 미리 등록한 교육용 DB(`hydops_edu`)를 확인하고, 제공된 클래스 매핑(설비·센서·SOP·조치는 그래프, 관측·사건·승인·조치 기록·재측정은 원천 DB 가상 연결)을 검토한 뒤 발행해 조회한다. 마지막으로 5회차 에이전트의 `get_asset_context` 도구 본체를 **플랫폼 어댑터**로 바꿔 끼우고, 같은 `asset_id` 에 대해 로컬 조회와 플랫폼 조회가 같은 판단 재료를 주는지 대조한다. 에이전트 코드는 한 줄도 바꾸지 않는다.

### 학습 목표
- Data Fabric 의 데이터소스 등록 정보·메타데이터·읽기 전용 질의로 교육용 DB 의 테이블과 행 수를 확인한다.
- Ontology Studio 매핑에서 graph 바인딩과 virtual 바인딩을 구분하고, 검증(`validate`)이 잡는 매핑 오류와 발행 전 조회 거부(409)를 재현한다.
- 발행된 스키마에서 객체 조회·관계 탐색·Behavior 호출을 실행하고, "발행"과 "데이터 존재"를 구분해 설명한다.
- `graph.asset_context` 와 같은 모양을 돌려주는 `PlatformContext` 를 고치고, HYD-01·HYD-02 에서 로컬과 플랫폼의 센서·적용 SOP·허용 조치가 같고 속성 차이만 있다는 것을 보인다.

## 2. 핵심 개념

![로컬 실습과 플랫폼 실습은 같은 함수를 부른다](../../materials/diagrams/D05_local_vs_platform.png)

### 2.1 교육용 플랫폼의 두 모듈

| 모듈 | 파일 | 오늘 쓰는 API |
|---|---|---|
| Data Fabric | `labplatform/fabric.py` | `GET /fabric/datasources`, `POST /fabric/datasources/{name}/query` (읽기 전용 트랜잭션, 쓰기 문장 거부) |
| Ontology Studio | `labplatform/studio.py` | `POST /studio/schemas/import`, `PUT .../classes/{c}/binding`, `GET .../validate`, `POST .../publish`, `POST .../objects/{c}/fetch`, `GET .../objects/{c}/{key}/related/{rel}`, `POST .../objects/{c}/behaviors/{b}/invoke`, `POST .../golden` |

### 2.2 그래프 바인딩과 가상 연결

제공 템플릿 `labplatform/templates/ontology_hydraulic.json` 의 9개 클래스는 두 종류로 나뉜다.

| 바인딩 | 클래스 | 원천 | 이유 |
|---|---|---|---|
| graph (label) | Asset · Sensor · SOP · Action | Neo4j 노드 | 설비·문서 지식은 관계 탐색이 필요하고 자주 바뀌지 않는다 |
| virtual (datasource·table·column_map) | Observation · Event · Approval · ActionLog · Verification | `hydops_edu` PostgreSQL 테이블 | 수치·실행 이력은 원천 DB 에 남긴다. 그래프로 복사하지 않는다 |

관계 8개 중 `HAS_SENSOR`·`GOVERNED_BY`·`ALLOWS` 는 그래프 관계, `HAS_EVENT`·`HAS_OBSERVATION`·`HAS_APPROVAL`·`HAS_ACTION`·`HAS_VERIFICATION` 은 속성 조인이다. `GOVERNED_BY` 는 그래프의 `APPLIES_TO` 를 **역방향**으로 읽고 `status = active` 만 남긴다.

```json
// lecture/system/labplatform/templates/ontology_hydraulic.json (발췌)
{"name": "GOVERNED_BY", "from": "Asset", "to": "SOP", "via": {"kind": "graph", "rel_type": "APPLIES_TO", "direction": "in", "where": {"status": "active"}}},
{"name": "HAS_EVENT", "from": "Asset", "to": "Event", "via": {"kind": "join", "from_property": "asset_id", "to_property": "asset_id"}}
```

> 주의: Neo4j 에 노드가 있다고 플랫폼 클래스가 되지 않는다. 클래스 매핑과 **발행**이 있어야 조회된다. 반대로 발행됐다고 데이터가 있는 것도 아니다. 발행 ≠ 데이터 존재.

> 주의: 교육용 플랫폼은 실제 플랫폼이 아니다. 같은 개념을 학생 노트북에서 돌도록 줄인 것이다. 대응 관계는 §10 에 정리한다.

```bash

show("validate bad", c.get(f"{P}/studio/schemas/{N}/validate"))
show("publish bad", c.post(f"{P}/studio/schemas/{N}/publish"))
c.put(f"{P}/studio/schemas/{N}/classes/Event/binding", json=ev["binding"])
```

### 흔한 실수
- Golden `answered: true` 를 "정답을 맞혔다"로 읽는다. 검증 함수는 각 단계 결과가 **비어 있지 않은지**만 본다. 위 HYD-02 실행에서 Q2 둘째 단계는 템플릿에 고정된 `SOP-COOL-001@v2`(HYD-01 SOP)의 조치를 조회하고도 `True` 였다. 질문 문구도 "HYD-01의…" 로 고정돼 있다.

- 클래스에 없는 속성으로 거른다. `Asset` 을 `{"educational": true}` 로 `fetch` 하면 `400 {"detail":"Asset 에 속성 educational 가 없다"}`, 정의되지 않은 관계를 따라가면 `404 {"detail":"relationship NOPE from Asset not defined"}` 가 온다. 로컬 그래프에 있는 속성·관계라도 매핑에 없으면 플랫폼에서는 없다.

| `GET .../validate`, `POST .../publish` → `_OntologyModel/_OntologyClass/_OntologyProperty` | Ontology Studio 발행 | 교육용 검증은 키 속성 1개·바인딩 존재·컬럼 존재만 본다. 발행 버전은 정수 증가, 이전 버전 조회 기능 없음 |
| `objects/{c}/fetch`, `related/{rel}` | 발행된 온톨로지 객체 조회·관계 탐색 | 교육용 필터는 속성 같음(`=`) 조건만, 페이지네이션 없음(`limit`) |
| Behavior `Asset.recent_state` (SQL 템플릿) | Ontology Studio Behavior | 교육용 Behavior 는 매개변수 SQL 한 문장. 코드 실행·권한 구분 없음 |
| `POST .../golden` | Golden Question 검증 | 교육용은 단계 결과가 비어 있지 않은지만 확인한다(정답 비교 없음) |
| 학생 `PlatformContext` 어댑터 | 에이전트의 온톨로지 조회 연결 | 교육용은 수업 코드의 도구 본체를 바꿔 끼운다. 실제 플랫폼의 에이전트 연결 방식은 7회차(MCP·업무 에이전트)에서 다룬다 |

**사전 준비**
- 서버: `scripts/servers.sh local 4`(강사). 5회차와 같은 로컬 오케스트레이션이다. 플랫폼 프로세스 모드는 7회차부터.
- `scripts/bootstrap_platform.py --upto ontology` 로 데이터소스 등록·메타데이터·기준 스키마 가져오기까지 한다. 기준 `HydraulicOps` 발행은 수업 시작 전 강사가 **한 번** 한다(`--upto publish`). 학생 발행은 팀별 `Lab_<팀>` 스키마로 한다. 기준 스키마를 여러 팀이 번갈아 가져오거나 발행하면 매핑이 덮이고 7·9회차 앱이 영향을 받는다.
- 활동 4 의 사건 ID 는 수업 DB 에서 HOLD_NO_EVIDENCE · CLOSED · SENSOR_CHECK 하나씩 골라 칠판에 적는다. HYD-02 사건이 있으면 FAN_BOOST 대조에 추가한다.
- 수업 뒤 팀 `Lab_` 스키마 정리: 교육용 플랫폼에는 스키마 삭제 API 가 없다. 강사가 `labplatform.db.delete('ontology', 이름)` 과 해당 `_OntologyModel {name}`·`_OntologyClass/_OntologyProperty {model}` 노드 삭제를 팀 이름별로 실행한다(`HydraulicOps` 는 제외). 리허설의 `Lab_P06_Textbook` 은 이 방법으로 지웠다.

**장애 대응**
- 교육용 플랫폼이 멈추면 활동 1~3 은 S11·S12·S13 스크린샷과 템플릿 JSON 읽기로 진행하고, 활동 4 는 lab 테스트 1부(가짜 응답)로 어댑터 논리를 완성한다. 이 경우 **플랫폼 실습 완료로 기록하지 않고** 7회차 시작 전 30분 보충에서 2부 테스트와 에이전트 교체를 다시 한다.
- `fetch` 가 409 면 기준 스키마가 발행되지 않은 것이다. 학생이 `HydraulicOps` 를 발행하지 않게 하고 강사가 발행한다.
- 메타데이터에 테이블이 없다는 검증 오류가 나면 강사가 `extract-metadata` 를 한 번 실행한다(학생은 실행하지 않는다).

## 용어

| 용어 | 뜻 |
|---|---|
| 교육용 플랫폼 (Lab Platform) | 실제 uEngine 플랫폼의 개념·API 모양을 수업 환경에 재현한 서버(:8910). 실제 플랫폼이 아니다 |
| 데이터소스 | Data Fabric 에 등록한 원천 DB 연결 정보. 오늘은 `hydops_edu`(읽기 전용 계정) |
| 메타데이터 추출 | 데이터소스의 테이블·컬럼 목록을 읽어 저장하는 것. 가상 연결 검증에 쓴다 |
| 클래스 매핑 | 온톨로지 클래스의 속성을 원천(그래프 라벨 또는 테이블 컬럼)에 대응시키는 정의 |
| graph 바인딩 | 클래스를 Neo4j 노드 라벨에 연결 |
| virtual 바인딩 (가상 연결) | 클래스를 원천 DB 테이블에 연결. 데이터를 복사하지 않고 조회 때 SQL 로 읽는다 |
| 발행 | 검증을 통과한 매핑을 버전으로 고정해 조회 가능하게 하는 것. 데이터 존재와 다르다 |
| Behavior | 클래스에 붙인 매개변수 조회(교육용은 SQL 템플릿) |
| Golden Question | 온톨로지가 답해야 하는 업무 질문과 그 조회 단계 |
| EKG | 설비·문서 지식과 원천 데이터를 연결한 기업 지식 그래프. 오늘은 발행된 `HydraulicOps` |
| 플랫폼 어댑터 | 에이전트 도구가 기대하는 모양을 유지한 채 조회 원천을 플랫폼 API 로 바꾸는 코드 |
| field_gaps | 한쪽(로컬)에만 값이 있는 속성 목록. 판단 재료 불일치와 구분한다 |
